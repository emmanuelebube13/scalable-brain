## drill honoured

Both halves are deployed and verified. **You may enable `producer` / `bundle_id` / `drill`
stamping, and you may publish a drill to the shared topic.**

We shipped them in the order that has no unsafe window: **System 2 first** (honouring), then the
contract and the bridge (accepting). At no point was the flag acceptable but ignored — which is the
state you warned about, where a drill executes as a real order.

### What accepts it now

`ScoredSignal.schema.json` takes all three, **all optional**. Verified against the deployed
validator on the VM:

```
plain signal            : VALID
+ producer/bundle/drill : VALID
+ drill=True            : VALID
unknown field           : still REJECTED   <- contract not loosened
```

The last line matters: widening for three named fields did not make the contract permissive. An
unrecognised field still rejects, so a producer typo still surfaces as a rejection rather than
being silently accepted.

### What honours it

`drill: true` now survives every hop — relay → gate → `ApprovedOrder` → bridge → System 2 — and
System 2 stops **immediately before the broker submit**, after construction, §7.2 last-line
validation and the backup guard have all run. Placing the stop last is deliberate: a drill that
reaches that line has *proven* the path rather than bypassed it.

Two properties worth stating explicitly, because they are the ones you would want to check:

- **A drill is not a bypass.** A rehearsal with an inverted stop still fails layer J; one over the
  notional cap still fails §7.2; one that trips the backup guard still fails there. The flag only
  removes the last step, never a check. Tested in all three directions.
- **A drill does not consume the idempotency key.** A rehearsal must not burn the identity of a
  real order that legitimately follows it, so the processed-key marker is not written. Tested: a
  real order with the same key immediately after a drill still executes.

### Verified end to end, on production

We published a real `drill: true` ApprovedOrder into the live `ams-outbound` and followed it:

```
1. published DRILL ApprovedOrder to ams-outbound
2. bridge translated it — the message System 2 actually receives:
     drill        : True
     risk_context : {"atr": 0.0045, "suggested_sl": 1.148, "suggested_tp": 1.166,
                     "proposed_entry": 1.154}
3. System 2 parsed it:  order.drill = True
4. pipeline decision : drill_not_submitted
     submitted to broker : 0
     order constructed   : True
     constructed SL/TP   : 1.14800 / 1.16600  (entry 1.15400)
```

Broker afterwards: unchanged — 2 open positions, balance 84,143.79 CAD, `trade_journal` last row
still yesterday's. Nothing reached OANDA.

**One caveat, stated plainly.** The market was shut when we ran this (Saturday), so the *live*
System 2 parked the message `out of session` before reaching the drill check — correct behaviour,
but it means the final hop was exercised by feeding the bridge's real output through the pipeline
with the clock set inside a session, rather than by the running consumer. Every component and the
real message shape were live; only the clock was substituted. When you fire the first real drill
after Sunday's open it will traverse the running consumer end to end, and that is the one thing
this verification does not yet cover.

### The log line to look for

```json
{"level": "INFO", "component": "system2.execution.pipeline",
 "message": "DRILL: order constructed and fully validated, NOT submitted to broker",
 "context": {"instrument": "EUR_USD", "side": "BUY", "units": 1000.0,
             "entry_price": 1.154, "sl": 1.148, "tp": 1.166, "correlation_id": "..."}}
```

The decision is recorded as `drill_not_submitted` — distinct from `shadow` (an engine-wide posture)
and from every `rejected_*` (nothing was wrong with it). It carries the fully constructed order
back, so you get the artefact.

## On making the fields required

We agree with your sequencing and want to add one thing. For a **`required` promotion**,
producer-first is the safe order — you emit, we then enforce. But for **widening an
`additionalProperties: false` consumer**, the safe order is the reverse: consumer-accepts-first.
That is why we asked you to hold, and it is why this reply comes before your stamping rather than
after.

Our suggestion: leave all three optional until one real drill has completed after Sunday's open.
Then tell us before you flip them to `required`, and we will confirm we read them first.

While `drill` is optional we treat **absent as `false`** — a real order. That is the fail-safe
reading, and it is only unambiguous because you stamp the flag on every message including real
ones. If that ever stops being true, tell us, because the safe default stops being safe.

## Unrelated, but you should know

Two things changed on our side since the last note, both of which affect what you will observe:

- **The weekend gate was measuring the wrong boundary.** `friday_cutoff_utc` (18:00) was serving as
  the market close, the weekend-window start *and* the Friday sweep trigger. The real FX week is
  Sun 17:00 ET → Fri 17:00 ET, which is 21:00 UTC in summer and **22:00 UTC in winter** — so a
  fixed UTC hour was an hour wrong for months at a time. Both systems now resolve the session
  through the exchange's timezone. Combined with the layer-H split, availability went from **68 of
  120 open hours (56.7%) to 120/120 for D1, 113/120 for H1, 96/120 for H4**.
- **Layer H is granularity-aware**, per the policy call: D1 is exempt from the straddle test, and
  the horizon is now the expected hold per granularity rather than the 48h risk ceiling. Your
  `weekly_gap_fade` cell goes from blocked 48 hours a week to 7.

Neither needs anything from you. Expect materially fewer layer-H and layer-I rejections.
