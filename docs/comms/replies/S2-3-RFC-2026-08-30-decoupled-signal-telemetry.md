## 1. Problem Statement & Objectives

* **Missing Gate 1 Telemetry:** System 1 currently publishes only approved signals to Pub/Sub (`scored_signal_queue`), while refused and unscored signals are discarded in-memory. Consequently, runtime approval rates cannot be computed due to a missing denominator.
* **Transport Disconnect & Coupling Risk:** System 1 and Systems 2/3 run on separate hosts without a shared database. A distributed transaction or synchronous remote database write is prohibited to protect execution latency and system isolation.
* **Schema & Technical Debt:** The existing `fact_signals` table belongs to a retired batch pipeline, lacks a UUID column, and cannot support the current real-time scoring contract. However, it is still dangerously wired into live dashboard APIs.

### Core Objectives

1. Implement a non-blocking, synchronous, local append-only log in System 1 for 100% of generated trade candidates to guarantee crash safety.
2. Establish a scalable transport bridge using Google Cloud Storage (GCS) to move logs across hosts without database coupling.
3. Enable offline reconciliation across Gate 1 (ML Gatekeeper) and Gate 2 (System 3 Risk Gate) via strict `signal_id` UUID matching.

## 2. Signal Classification States (Gate 1)

Every candidate generated by System 1 must be assigned a UUID at *candidate creation* (pre-scoring) and categorized into one of three explicit states:

| Outcome State | Condition / Trigger | Wire Action | Telemetry Semantics |
| --- | --- | --- | --- |
| **`approved`** | Model score meets or exceeds the regime threshold. | Published to Pub/Sub topic `scored_signal_queue`. | Counted in the approval rate numerator and denominator. |
| **`refused`** | Model score falls below the regime threshold. | Dropped from wire transmission. | Counted in the approval rate denominator only. |
| **`unscored`** | Strategy is unmapped or unknown to champion model (`model_score: null`). | Handled via fallback routing (`emit-unscored` branch). | **Excluded** from ML approval rate math to avoid statistical distortion. |

## 3. System 1 Implementation Plan (Producer & Gate 1)

### 3.1. Local Write & Cross-Host Transport

* **Storage Location:** System 1 will execute a synchronous local append to an NDJSON ledger per run. **No direct database writes are permitted from System 1.**
* **Crash Safety:** Batching in-memory is prohibited. The synchronous append ensures that if the script crashes post-scoring, the record survives. A failed log write must be caught locally but must not block signal emission to Pub/Sub.
* **Transport:** The NDJSON ledger is pushed to `gs://scalable-brain-artifacts/system1/signals/`. An asynchronous ingester will later pull this into the telemetry database.

### 3.2. Mandatory Log Schema

* `signal_id`: UUID (Minted at candidate creation. This is the **sole** join key; composite keys are strictly prohibited).
* `produced_at`: ISO-8601 UTC timestamp.
* `pair`: Currency pair symbol.
* `direction`: `BUY` / `SELL`.
* `strategy_id` & `strategy_key`: Originating strategy identifiers.
* `regime`: Market regime classification at scoring time (e.g., `High-Vol`, `Ranging`).
* `model_score`: Gatekeeper probability output (`FLOAT` or `NULL` if unscored).
* `threshold_applied`: Numerical cutoff applied for the active regime.
* `gate1_outcome`: `approved` | `refused` | `unscored`.
* `scoring_status`: Provenance flag (e.g., `scored`, `unscored_unknown_strategy`).
* `gatekeeper_artifact_sha`: SHA-256 hash of the active champion model bundle.
* `proposed_levels`: Entry, stop-loss, and take-profit levels proposed by System 1.

## 4. Systems 2 & 3 Support Plan (Consumer & Gate 2)

## 5. Offline Reconciliation & Telemetry Domain Rules

### Telemetry Formulations

* **Gate 1 Approval Rate (Per Regime):** approved / (approved + refused), per regime.
* **Network Drop Detection:** Signals flagged as `approved` in System 1 that do not appear in `ams_decision_log` will be flagged as dropped wire messages.

### UI & Domain Guardrails

1. **Minimum N Rule:** The dashboard must not render a percentage for any regime containing fewer than 30 samples (`min_regime_n: 30`).
2. **Anti-Conflation:** The UI must explicitly label metrics (e.g., "Runtime Approval Rate" vs. "OOS Calibration Rate"). A lone, unlabelled scalar is prohibited.
3. **Retention:** NDJSON files in GCS will follow a standard 90-day hot storage retention policy.
