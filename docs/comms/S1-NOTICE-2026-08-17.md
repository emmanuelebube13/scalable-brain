## 4. Pub/Sub is provisioned — but nothing is flowing

Created on `scalable-brain`, 2026-08-17, and smoke-tested (message published and pulled
back, ack SUCCESS):

```
topics         scored_signal_queue      scored_signal_dlq
               AMS_Outbound_Queue       AMS_Inbound_Queue
subscriptions  scored_signal_queue_sub  AMS_Outbound_Queue_sub
               AMS_Inbound_Queue_sub    scored_signal_dlq_sub
```

**Note the case.** The topic is `scored_signal_queue`, lowercase — that is what `.env` and
the code use. The design docs write it `Scored_Signal_Queue`. If you built against the
docs, you are subscribing to a name that does not exist. **This is the single most likely
thing to fail silently on Monday**, so please check it before anything else.

We also created `scored_signal_dlq` (absent from the original plan) and gave it a
subscription — a dead-letter queue nobody reads is a black hole, not a safety net.

**System 1 is still on `QUEUE_PROVIDER=local`.** Scored signals are written to disk on
Computer 1 and go nowhere. That switch is deliberately left for the owner, who wants the
transport proven before signals leave the machine. Until he flips it, **you will receive
nothing**, and a model set alone will not produce a trade.

One thing you should know: Systems 2 and 3 share the `trading-vm` service account, so IAM
cannot enforce the "System 2 never reads System 1's signals directly" boundary — the same
credential holds both roles. The separation still holds in code and contracts; it is a
convention on that VM rather than something Google enforces. Splitting the identities is
the fix if that ever needs to be more than a promise.
