## ISSUE-1 — System 3 runs an unmerged branch, and deploying `main` would silently kill the wire

**Severity: 1 (latent total signal loss, one `git pull` away).**

The live System 3 on `trading-1` is running commit `5b66039`. That commit is **not an ancestor
of `origin/main`** — `git branch -r --contains` lists five feature branches and omits `main`.

The deployed `contracts/v1/ScoredSignal.schema.json` hashes to
`0856914c1d5a93cb...`, which matches **`origin/feat/adr001-reanchor-and-drills` exactly** and
differs from `origin/main` (`16c4a315d7ca33e1...`).

The difference is load-bearing:

| Field | S1 emits it? | `feat/adr001…` accepts | `origin/main` accepts |
|---|---|---|---|
| `producer` | **yes, unconditionally** | yes | **no** |
| `bundle_id` | **yes, when `model_set_id` set** | yes | **no** |
| `drill` | **yes, on every message** | yes | **no** |

Both schemas set `additionalProperties: false`. `src/queue_producer/producer.py:176-185` stamps
all three on every message and has done since 2026-08-29, on the basis recorded in its own
comment: *"Systems 2 and 3 deployed a schema that accepts all three."* **That is true of the
deployed working tree and false of `origin/main`.**

So: anyone who redeploys System 3 from `main`, or merges `main` over the running tree, causes
**every System 1 signal to fail validation** — silently, at the consumer, with no change on this
side. That is the FIX-S1-016 failure mode approached from the opposite end.

### It is worse than a branch mismatch — the running tree matches no single commit

Tracing the file's history on `feat/adr001-reanchor-and-drills`:

| Commit | Date | ScoredSignal sha256 (16) |
|---|---|---|
| `0f51f21` | 2026-08-29 | **`0856914c1d5a93cb`** ← what is on the VM |
| `37859a2` | 2026-08-23 | `16c4a315d7ca33e1` (= `origin/main`) |
| `093cd22` | 2026-07-06 | `9187bc762f7ad4d6` ← **what `5b66039` contains** |

The VM's `.git/refs/heads/main` says `5b66039`, whose version of that file is the **July
baseline** (`9187bc76`). The file actually on disk is from `0f51f21`, **six weeks newer than the
revision the repo believes is checked out.**

So System 3 was not deployed by git checkout. Files were updated in place while the ref stayed
put. **The exact code placing real OANDA orders is not reproducible from any recorded
revision** — which contradicts the platform's own "deterministic, idempotent, auditable"
principle, on the one system whose job is to be the last line of defence.

**Action, in order:**

1. On the VM, capture the working tree as it actually is (`git stash`-free: commit it on a
   branch named for the fact, as `37859a2`'s own message did — *"commit the working tree as
   found"*). Until that exists, a VM rebuild loses the running configuration silently.
2. Merge `feat/adr001-reanchor-and-drills` into `main` so the widened contract is on the
   default branch.
3. Only then treat `main` as deployable.

Not actionable from this repo — these are System 3 changes and need a notice through
`docs/comms/to_system3/`.

**What I did not check:** the full extent of the drift. `git status` on the VM was blocked by
git's `dubious ownership` guard and I declined to write `safe.directory` into the VM's git
config, so **the contract file is the only drift I positively confirmed.** There may be more,
and given how it was found, assume there is until someone runs a clean diff.

## ISSUE-2 — Every signal System 3 has decided was rejected at Layer H or I

**Severity: 2 (this, not the circuit breaker, is what is stopping trading).**

`localhost:8300/health` on `trading-1`, read 2026-09-13:

```
"state":"ACTIVE", "mode":"enforce"
"decisions_rejected": 6, "decisions_rejected_total": 6
"rejects_by_layer": {"H":3,"I":3}
"decision_latency_ms": {"samples":6}
```

Six signal decisions in ~10 days of uptime, **six rejections, zero approvals** — three at Layer
H (duration gates) and three at Layer I (weekend / holiday / macro windows). System 2
corroborates from the other side: `messages_seen: 0`, `last_message_at: null` over 870,880 s of
uptime. S3 approved nothing, so S2 received nothing.

These are **session and timing gates, not risk gates and not evidence gates** — they reject on
*when* a signal arrived, not on whether the strategy has an edge. Per
`docs/goals/VISION.md` §4 that puts them squarely in the adjustable column.

There is already an unmerged fix branch for exactly this:
`origin/feat/gate-time-rules-and-straddle` — *"feat(gate): decouple Layer H hold from risk
ceiling and add DST-aware NY time rules."*

**Trap:** that branch carries `origin/main`'s narrow ScoredSignal schema
(`16c4a315…`), so merging it alone fixes Layer H **and breaks the wire per ISSUE-1.** The two
merges have to land together, or `adr001` first.

## ISSUE-3 — Three repo documents describe a topology that does not exist

**Severity: 3 (misleads every agent that reads them, including on first load).**

There is no Computer 2 and no Computer 3. Both System 2 and System 3 run as services on a
single GCP VM, `trading-1` (europe-west1-b, e2-medium, internal IP only — SSH requires
`--tunnel-through-iap`). `data/systems/system-2.json` in the architecture hub states it plainly:
*"not a separate Computer 2"*; system-3: *"there is no Computer 3."*

- `CLAUDE.md` — the three-system table gives S2 and S3 as "user's other computer" / "trading-1"
  as if distinct hosts.
- `README.md` — an ASCII topology diagram of three computers, plus dead links to
  `../system-2-execution-engine/ARCHITECTURE.md` and
  `../system-3-account-management/docs/ARCHITECTURE_OVERVIEW.md`.
- **19 references across 6 files** point at `../system-2-execution-engine/` or
  `../system-3-account-management/`. **Neither directory exists on this machine** and neither
  matches a real repo name (`system2Executor`, `scalablebrain-ams`).

Also stale, and worth correcting in the same pass: `CLAUDE.md`'s standing claim that the S1/S3
signal schemas are *"mutually incompatible (`instrument`/`pair`, `entry`/`proposed_entry`, …) so
every signal System 1 produces would be rejected."* **That reconciliation already happened** —
`contracts/signal-message-contract.json` in this repo carries
`$id: https://scalablebrain/ams/contracts/v1/ScoredSignal.schema.json` and an identical
`required` list to System 3's. System 1 adopted System 3's names, as instructed. The live
blocker is ISSUE-1 (three extra fields), which is a much narrower and different problem.

**Action:** topology + dead paths + the retired schema claim, one change set.
