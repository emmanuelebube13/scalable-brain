## 1. CRITICAL — nothing on a schedule advances `fact_market_regime_v2`

**Status:** open. This is now the *only* red light on the heartbeat, and it is telling the truth.

```
fact_market_prices        max ts  2026-08-14 20:00Z
fact_market_regime_v2     max ts  2026-08-11 13:00Z    (H1 08-11 13:00 · H4 08-11 09:00 · D1 08-09 21:00)
```

**The non-obvious part.** The regime table is not refreshed by the weekly ingest.
`shell/cron_oanda_ingest_saturday.sh` runs exactly one script —
`src/layer0/ingest_data/ingest_oanda_prices.py` — which advances prices and nothing else. The only
scheduled caller of the regime step is `_default_pipeline()` in
`src/system1/scheduler/orchestrator.py:299`, which runs `hmm_regime.run()` as stage 1 of a retrain.

That orchestrator is the hourly cron **disabled on 2026-08-02** at Computer 2's request — the same
pause T4 just taught the heartbeat to accept.

So the two things are the same decision seen from two sides. T4 correctly silenced the checks that
were only reporting *"the cron is off"*, because that was noise. But the cron being off also
produces a genuine and growing data gap, and `regimes` is the check that sees it. It will fall
further behind by roughly seven days per week for as long as the hold stands, and the hold is
declared until **2026-09-15** — about 34 days of drift by then.

**Why this matters beyond the alarm.** Attribution joins trades to the regime at entry. Every
score computed while the regime table trails the price table is computed against a market state
the system has not measured yet.

**What is worth deciding (not doing here):**
- Regime labelling is read-only with respect to the champion bundle — it writes
  `fact_market_regime_v2`, it does not promote anything. Computer 2's objection was to a
  *promoter* running against the shared bucket, not to the regime step. A standalone
  `hmm_regime` cron would honour their request and close this gap. That is a decision, not an
  obvious fix, which is why it is written down rather than done.
- If instead the answer is "regimes stay stale until the retrain cron returns", then the honest
  move is a **declared hold on `regimes`** with that reasoning and the same expiry — the
  machinery for it now exists. What must not happen is the check staying red indefinitely with
  nobody deciding which of the two it is.

**Verify:**
```bash
python -m src.system1.monitoring.heartbeat --check regimes
psql -h localhost -p 5432 -U sa -d ForexBrainDB \
  -c 'SELECT granularity, max("timestamp") FROM fact_market_regime_v2 GROUP BY granularity;'
```

## 2. LOW — `--holds` prints holds that are not in force

`heartbeat.py --holds` iterates the parsed holds and then prints problems underneath. But when a
holds file has *any* problem, `run_checks()` applies **no** holds from it
(`active_holds = {} if holds_problems else holds_by_check`). So a file with one good hold and one
bad one prints the good hold as though it were active, when nothing is being suppressed.

The heartbeat's own behaviour is correct — fail-loud. Only the human-facing listing is misleading,
and only in the malformed case.

**Fix when convenient:** in `main()`, print `NOT IN FORCE — the holds file has problems` above the
listing whenever `problems` is non-empty.

---

## 3. LOW — a broken holds file reports only its first problem

`summarise()` in `holds.py` returns `problems[0]`. Fix three bad holds and you learn about the
next one only on the following run. Consider joining them, or appending `(+2 more)`.

## Resolved on 2026-08-15 — recorded so the fix is not re-litigated

Both fixed in commit `b81ff03`, tests green (`src/system1/monitoring` 41 passed, `src/system1`
288 passed).

- **`CheckResult.to_dict` dropped a healthy `underlying_status`.** It tested the enum for
  truthiness and `Status.OK` is `IntEnum` 0, so a held check whose underlying measurement was
  *healthy* serialised as `underlying_status: null` alongside `held: true`. That is precisely the
  state a hold ends in — the cron returns, the check goes green, the hold is still declared — so
  the snapshot lost provenance in the one case it most needed to keep it.
- **Monitoring tests read the real `results/state/cron_holds.json`.** `run_checks()` reads
  `HOLDS_FILE` and the sandbox fixture never redirected it, so three tests depended on live repo
  state. A declared hold on `telemetry` would have silently broken
  `test_blocked_check_fails_the_run`. An autouse fixture now points `HOLDS_FILE` at a nonexistent
  path.
