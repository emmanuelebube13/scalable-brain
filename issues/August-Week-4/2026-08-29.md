## 1. Running the test suite writes the LIVE emitter state — and it reaches shared telemetry

**Status: FIXED.**

`src/signals/tests/test_producer.py::test_missing_model_set_emits_nothing` patches
`load_model_set` to return `None` and then calls the real `run_once`. `run_once` reaches
`record_emitter_state("no_model_set")`, which writes the repo's real
`results/state/signal_emitter_state.json` — the file `src/monitoring/publish_health.py`
uploads to `telemetry/s1_health.json` on every hourly cron.

So `pytest` manufactures a System 1 producer fault that never happened, and the next
hourly run publishes it to the bucket Systems 2 and 3 read.

**Evidence — caught in the act today:**

```
09:07:20Z   full test suite run
09:07:20Z   mtime of results/state/signal_emitter_state.json   <- same second
            last_run_outcome  : no_model_set
            consecutive_faults: 1
            last_healthy_run_at: 2026-08-29T08:15:20Z          <- the real 08:15 cron run
08:15:20Z   the last actual producer run, healthy (log: "No signals generated")
```

The hourly cron fires at `:15`. Nothing of ours runs at `:07`. The `09:15:16Z` run cleared
it — `no_signals_generated`, `consecutive_faults: 0` — which is the self-clearing behaviour
working, but it clears a fault that was never real and it does so only after the false
value has been published to the bucket.

**This is a live candidate for the `no_model_set` that could not be reproduced** in
`TO-SYSTEM2-3-2026-08-28-stamping-disabled-erratum.md` §6. Both faults recorded there —
`17:36:31Z` on 08-28 and the `12:19:21Z` one it describes — are at minutes no cron fires
at, and the erratum reports two storage hypotheses tested and disproved. A test run is
consistent with every symptom: it needs no misconfiguration, leaves no producer log line,
and self-clears on the next real run. **Not proven** — nothing records when the suite was
run on those days — but it is the first hypothesis that fits, and it now cannot recur.

**Fix:** an `isolated_emitter_state` fixture repoints `run.EMITTER_STATE` at `tmp_path` for
the two tests that call `run_once`, plus
`test_run_once_never_writes_the_live_emitter_state`, which asserts the live file's mtime is
unchanged across a `run_once` call. The isolation is load-bearing, so it is asserted rather
than assumed.

**Not checked:** whether any other test writes a live artifact under `results/`. This was
found by matching one mtime, not by an audit. `results/state/watcher_state.json` is the
obvious next candidate — `test_watcher_state_filters_seen_bars` patches
`watcher.save_state`, so it looks deliberate there, but the pattern deserves a sweep.

## 2. We told Systems 2 and 3 to read two fields we do not publish

**Status: FIXED.**

The erratum of 2026-08-28 §6 says, in a message already sent:

> **Read `consecutive_faults` and `last_healthy_run_at`, not `last_run_outcome` alone.** A
> single fault beside a recent healthy run is a blip; a rising count is an outage.

`publish_health.collect()` built its `emitter` block from seven fields, and neither of
those two was among them. Both exist in the local state file; neither left this machine.
From the outside the distinction the advice depends on was not merely hard to make — it
was unavailable, and the only visible field was the one they were told not to trust alone.

**Fix:** both are added to the published payload, with
`src/monitoring/tests/test_publish_health.py` pinning them (the module had no tests).
Reported in `TO-SYSTEM2-3-2026-08-29-stamping-enabled.md` §5 so the receiving operator
knows the advice only became actionable today.

**Not checked:** whether the dashboard renders them, or whether anything downstream alerts
on `last_run_outcome` alone.
