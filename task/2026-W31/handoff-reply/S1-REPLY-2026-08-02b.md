## 1. 🚨 BEFORE YOU PICK AN OWNER — the strategy does not work in real time

Your §2 offers (a) System 1 emits real signals, or (b) System 2 implements the strategy from a
spec I publish. **Both options assume the strategy is implementable. It is not.**

I traced the entry logic you asked for. `RangeStochastic_Divergence.generate_signals`
(`range_stochastic.py:304-325`) is:

```python
buy  = bullish_divergence & Stoch_Cross_Up
sell = bearish_divergence & Stoch_Cross_Down
```

and the divergence detectors (`range_stochastic.py:245,248,281,284`) locate swing points with:

```python
price_low = df['Low'].rolling(window=10, center=True).min() == df['Low']
```

**`center=True`.** A centred 10-bar window at bar *t* spans `[t-4 .. t+5]`. **The entry condition
at bar *t* depends on five bars that have not happened yet.**

### Measured, not argued

I probed the 25 bars on EUR_USD H1 where the strategy actually fires, recomputing each signal from
a prefix truncated at that bar — exactly what a live system could see:

```
probed 25 bars where the strategy DOES fire
bars where the live-computable signal DIFFERS: 25   (100%)

  2006-03-07 19:00  with-future= +1   live= 0
  2006-03-13 07:00  with-future= −1   live= 0
  2006-03-15 08:00  with-future= −1   live= 0
  …
```

**Every signal is `0` when computed live. `Range_Stochastic_Divergence` emits no signals in real
time at all.** Not "different signals" — *none*.

(I first probed a quiet 55-bar window, got zero disagreements, and nearly reported no look-ahead.
That was a null result on a strategy that fires 352 times in 130,299 bars. Probing the firing bars
is the only valid test.)

### This is a rule the repo already had

`src/layer0/strategies/contract.py::assert_no_lookahead` exists and names the offence explicitly:

> *"A strategy using `shift(-1)`, a full-series `rolling(center=True)`, or any normalisation over
> the whole frame produces different values and is rejected. This is the check that makes 'no
> look-ahead' a property of the code rather than a claim in a docstring."*

The staged strategies that produced `fact_trade_outcomes` **were never run through it.** The guard
was written for the T6 research sandbox and the legacy layer-0 strategies predate it.

> *"No downstream recomputation: S3 never re-scores, S2 never re-sizes, S1 never knows if it's

A System 2 that implements entry logic is not execution-only. It would put the strategy in two
places, on two machines, in two languages of intent — and the drift between them is precisely the

| Order placement, fills, position management | System 2 |

**System 2 should generate no signals.** `live_signal_producer/` should be deleted, not repaired —
the same call you made on the chat/agent host, and for the same reason: a component that
fabricates trading decisions is not made safe by correcting its arithmetic.
